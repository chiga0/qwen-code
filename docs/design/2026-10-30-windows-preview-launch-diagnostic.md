## Problem and observed baseline

The [original Windows ECS case](https://github.com/QwenLM/qwen-code/actions/runs/41002095690/job/123897020864) rejected a deliberately truncated archive, then passed the comparison proving the previous installation tree was unchanged. Launching the retained `qwen.cmd` subsequently produced empty stdout instead of `OLD_PREVIEW`. That failure does not establish installer file deletion.

A [hosted Windows pre-install diagnostic](https://github.com/chiga0/qwen-code/actions/runs/41030003395/job/123977212631), on `515b8d67`, reproduced the empty stdout before invoking any installer. The PowerShell wrapper process returned status 0, signal null and error null. The fixture omitted `PATHEXT`, while the parent contained `.CMD`; the child reported only `.CPL`. Node was `v22.23.4` and Windows PowerShell was `5.1.20348.5756`. The unchanged `OLD_PREVIEW` assertion failed. This is a real RED observation, not a successful launcher or installer qualification.

A second [Windows run](https://github.com/chiga0/qwen-code/actions/runs/41031170132) on `0bbcad` inherited the real parent `PATHEXT`. Raw stdout was now `OLD_PREVIEW`, and both launcher checks and the no-staging check completed. The case still failed: after the launches, the protected fixture HOME gained `AppData/Local/Microsoft/Windows/PowerShell/StartupProfileData-NonInteractive` and roaming directories. Its `.profile` stayed unchanged. The whole-file result was 1 failure and 3 declared POSIX skips; other cases were not reached after bail. This remains a fixture-protection failure, not a whole-file pass.

## Candidate change and scope

Preserve the parent's actual `PATHEXT` in the Windows-only fixture environment alongside `SystemRoot` and `ComSpec`. Do not invent a default extension list, weaken the stdout assertion or change the installer. The second Windows observation confirms restored launcher output on that candidate, while its subsequent HOME-protection failure remains unresolved. All earlier failures remain recorded.

Keep the pre-install testcase's two distinct launcher observations: first the original PowerShell expression with six `QWEN_DIAG_` stderr records: the original `PATHEXT`, `COMSPEC`, `SYSTEMROOT`, PowerShell version, plus actual `GetFolderPath(LocalApplicationData)` and `GetFolderPath(ApplicationData)` paths; then, only if that qualifies, the strict old-installation check. Capture complete process error, signal, status, stdout and stderr. Require trimmed stdout `OLD_PREVIEW`, exactly one of each diagnostic record (values may be empty), and no additional stderr. The second check requires a native exit code, preserves the installation-tree assertion and confirms no staging directory. Its two checks invoke **zero installers** and at most two launcher processes, in addition to the one fixture-readiness launch described below, with no retry. Other preservation cases exercise the real installer separately.

The subsequent `329ccc` candidate tried two arbitrary owned `APPDATA` and `LOCALAPPDATA` environment paths. The actual known-folder observation returned an empty LocalApplicationData path and an ApplicationData path under HOME instead, so its exact routing assertion failed before any installer. Retain that failure. Remove those unsupported environment overrides, extra directories and routing equality assertions; the six raw diagnostic records remain observations rather than a redirection contract.

The next candidate initializes each Windows fixture once through the existing strict public old-launcher check after seeding it, before any archive creation or installer invocation. Require exact `OLD_PREVIEW`, status 0 and empty stderr. Save the complete cold HOME map and initialized HOME map, including every added entry, to the structured test log. Every pre-existing cold entry must keep its type, mode, hash and link target. Only then freeze the complete initialized HOME as the preservation baseline. A method returned by the fixture performs initialization exactly once inside the existing `withFixture` `try`, before the test actions, so readiness or cold-entry assertion failures also reach the original `finally` cleanup of the owned root. Do not catch or suppress the first error. HOME and USERPROFILE remain the same owned directory; no profile split or cache exclusion is introduced. The subsequent actual Windows run on `575d` still failed: readiness added only AppData, Local and Roaming, and the next two zero-installer launches added the Microsoft, Windows and PowerShell directories plus `StartupProfileData-NonInteractive`. Retain that whole-HOME failure; do not add further warmups or waits to seek cache stability.

The new contract explicitly preserves user data with an exact OS-derived additions domain; it no longer claims the entire HOME is identical. Every existing cold-map and initialized-baseline entry, including any pre-existing same-name cache, must retain its type, full mode, file bytes/hash or link target. Only four exact relative paths absent from both baselines may be added: the directories `AppData/Local/Microsoft`, its `Windows` child and its `PowerShell` child, plus the regular file `StartupProfileData-NonInteractive` below them. Every parent must be a real directory without following links. A directory impersonating the cache file, any link, or any other addition, mutation or deletion is rejected. Structured logs preserve complete cold, initialized and current maps and separate derived-domain before/after rows. Regular rows record lstat type, full mode, bytes and SHA; directory rows record type and full mode and have no file-content bytes/SHA.

The actual zero-installer control establishes these paths can appear during host startup, without identifying a unique writer PID. A map comparison cannot distinguish an installer writing into the same exact new domain; this contract makes no such attribution. Portable contract tests use the same validation helper as the real fixture: a positive four-entry addition and negative profile mutation, unrelated addition, directory impersonation, cache link, parent-chain link and mutation of a baseline-existing cache. All four historical failures remain failures.

This establishes an initialized profile with a publicly launchable old installation before testing preservation; it does not prove a pristine HOME receives no PowerShell host writes. The pre-install testcase has one readiness launch in fixture setup followed by its two existing diagnostic/check launches, all with zero installers and no retry. Other preservation cases also receive exactly one readiness launch per Windows fixture.

The existing `windows-runner-smoke.yml` retains its boolean `preview_launch_diagnostic`, default `false`. The default full ECS job and its preinstalled Node path remain in place. The `true` mode now runs the **entire preview installer test file once** (12 installer/diagnostic cases plus seven portable contract cases), without a test-name filter; it no longer means a single zero-installer workflow job. It includes the pre-install testcase and the original preservation cases, retaining their assertions and declared platform skips. The current file registers 19 cases; Windows is expected to execute 16 and declare three POSIX skips, subject to actual verification. It does not run the whole repository suite or build workspaces.

This focused hosted `windows-2022` job uses Node 22, the shared Windows environment action, exact checkout verification, frozen `--ignore-scripts` dependency installation, zero retries, one worker, a 15-minute bound and an always-uploaded log. Workflow meta-tests protect selection, error propagation and the unchanged default ECS path. The five-file change is limited to the fixture/diagnostic test, workflow, its meta-tests and these two design documents.

## Validation and limits

Run the complete script test and workflow meta-test file through `scripts/tests/vitest.config.ts`, formatting and applicable static checks. macOS can validate POSIX cases and workflow wiring; Windows-only skips there are not Windows evidence.

After review, dispatch the exact candidate branch with `preview_launch_diagnostic=true`. Record actual checkout, runner, Node and PowerShell, inspect the raw launch records and report the whole file's actual pass/fail/skip counts. The first raw launch must again satisfy the original `OLD_PREVIEW` oracle before the subsequent strict check; preserved-tree and staging assertions remain required for installer cases. The new user-data plus exact-derived-additions contract still requires Windows verification; portable map tests do not qualify the hosted Windows or installer behavior.

Hosted Windows is not the original ECS host. A new successful file run would qualify that fixture and preservation file on the recorded candidate/environment, not all Windows product behavior or the original ECS result. No production default, renderer, release or installer behavior changes here.
